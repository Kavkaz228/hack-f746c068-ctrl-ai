# Career Quest API

## Запуск и доступ

В общем приложении (`python -m backend.web` или Docker) интерфейс и API работают
на одном адресе, все пути ниже — с префиксом `/api`, например `/api/health`.
Отдельный API для разработки frontend: `python -m backend.api` → `http://127.0.0.1:8000`
без префикса. Swagger (`/docs`) и OpenAPI (`/openapi.json`) открыты только в режиме
разработки или при `CAREER_QUEST_ENABLE_DOCS=true`; в продакшне скрыты.

### Аутентификация

- **Люди** входят по почте и паролю: `POST /auth/login` ставит cookie `cq_session`
  (httpOnly, SameSite=Strict, Secure при HTTPS). JavaScript её не видит; токен
  в базе хранится только как SHA-256. Срок сессии — `CAREER_QUEST_SESSION_HOURS`
  (12 ч), простой — `CAREER_QUEST_SESSION_IDLE_MINUTES` (120 мин).
- Для запросов с cookie, меняющих данные, проверяется заголовок `Origin`/`Referer`:
  он должен совпадать с адресом сайта или `CAREER_QUEST_TRUSTED_ORIGINS`.
- **Сервисные клиенты** (интеграции, тесты) передают `Authorization: Bearer <token>`;
  такие учётные записи не создаются через интерфейс.
- После 5 неверных паролей учётная запись блокируется на 15 минут; с одного IP —
  не более 30 попыток входа за 15 минут. Ответ на неверную почту и неверный пароль
  одинаковый.
- Пока пользователь не сменил временный пароль или не дал согласие на обработку
  персональных данных, бизнес-маршруты отвечают `403` с кодом
  `password_change_required` или `consent_required`; доступны только `/auth/*`.

Регистрации нет: учётные записи создаёт HR (`POST /users`) или оператор
(`python -m backend.manage create-user`). Первый HR создаётся из
`CAREER_QUEST_BOOTSTRAP_HR_EMAIL`/`CAREER_QUEST_BOOTSTRAP_HR_PASSWORD`, если
пользователей нет. В режиме разработки без пользователей создаются два
демо-аккаунта, пароли записываются в `backend/runtime/demo-credentials.txt`.

## Маршруты

| Метод и путь | Доступ | Ответ |
| --- | --- | --- |
| `GET /health` | Все | `{"status":"ok"}` — процесс жив |
| `GET /ready` | Все | `{"status":"ready"}` или 503, если база недоступна |
| `GET /metrics` | Токен метрик | Счётчики в формате Prometheus |
| `POST /auth/login` | Все | Identity и cookie сессии |
| `POST /auth/logout` | Все | Отзыв сессии и удаление cookie |
| `GET /auth/me` | Авторизованные | ID, роль, employee_id, имя, почта, `must_change_password`, `consent_required`, `completion_mode` |
| `POST /auth/password` | Вошедшие по паролю | Смена пароля; другие сессии пользователя завершаются |
| `POST /auth/consent`, `DELETE /auth/consent` | Авторизованные | Согласие на обработку ПДн (с версией) и его отзыв |
| `GET /users`, `POST /users` | HR | Учётные записи; создание возвращает временный пароль один раз |
| `POST /users/{id}/reset-password` | HR | Новый временный пароль, сессии пользователя отзываются |
| `POST /users/{id}/disable`, `/enable` | HR | Отключение и включение доступа |
| `GET /employees` | HR | ID, имя, роль и грейд всех сотрудников |
| `GET /hr/employees` | HR | Все сотрудники с готовностью, разрывами и следующим шагом — одним запросом |
| `GET /employees/{id}` | Сам сотрудник или HR | Профиль, трек, история, справочник навыков, gaps, readiness, recommendations, `pending_completions` |
| `GET /employees/{id}/recommendations?limit=3` | Сам сотрудник или HR | Детерминированные рекомендации с объяснением; limit 1–3 |
| `POST /employees/{id}/ai/recommendations` | Сам сотрудник или HR | GPT-выбор первого шага с локальным запасным вариантом; 429 при исчерпании лимита |
| `GET /employees/{id}/comparison-options` | Сам сотрудник или HR | Все полезные активности, в порядке оценки |
| `GET /employees/{id}/simulate/{event_id}` | Сам сотрудник или HR | Прогноз без сохранения |
| `GET /employees/{id}/compare?first_event_id=A&second_event_id=B` | Сам сотрудник или HR | Сравнение двух активностей |
| `GET /events` | Авторизованные | HR: весь каталог; сотрудник: активные события своей роли |
| `POST /employees/{id}/activities/{event_id}/complete` | Сам сотрудник или HR | 200 — изменения применены; 202 — заявка ждёт HR (режим `approval`) |
| `POST /employees/{id}/activities/{event_id}/skip`, `/decline` | Сам сотрудник или HR | Запись пропуска или отказа и новые рекомендации |
| `POST /employees/{id}/promote` | HR | Перевод на следующий грейд |
| `GET /completion-requests?status=pending` | HR — все, сотрудник — свои | Заявки: `pending`, `approved`, `rejected`, `expired`, `all` |
| `POST /completion-requests/{id}/approve`, `/reject` | HR | Решение по заявке с комментарием |
| `GET /hr/dashboard` | HR | Средняя готовность, дефициты, сотрудники без шага, участие |
| `POST /dataset/import` | HR | Импорт или проверка без записи (`dry_run=true`) |
| `GET /dataset/snapshots`, `POST /dataset/snapshots` | HR | Снимки данных; ручное создание |
| `POST /dataset/snapshots/{id}/restore` | HR | Восстановление; текущее состояние сначала сохраняется в снимок |
| `GET /dataset/export` | HR | Весь набор одним JSON-файлом |
| `GET /audit?limit=100&before_id=&action=` | HR | Журнал действий, новые сверху |

Формат ошибок: `{"error":"код","message":"описание"}`, ошибки валидации также
содержат `issues`. Статусы: 401 — не выполнен вход, 403 — нет прав, не тот
источник запроса (`csrf_failed`), нужен новый пароль или согласие; 404 — нет
профиля, события или заявки; 409 — конфликт ID, ключа повтора, уже принятое
решение; 413 — слишком большой запрос или файл; 422 — некорректные данные или
не выполнены требования; 429 — лимит попыток входа или GPT; 503 — база недоступна.
Каждый ответ содержит `X-Request-ID` (можно передать свой) — по нему запрос
находится в JSON-логах сервера.

HR-ответ содержит `average_readiness_percent` по сотрудникам, у которых есть
следующий грейд, и `role_skill_deficits`. Для каждой пары роль/навык там указаны
`eligible_employees`, `affected_employees` и `average_gap_across_role`.
Расчёт кэшируется по версии данных и пересчитывает только изменившихся сотрудников.

## Прогноз и сравнение

`GET /employees/E001/simulate/EV002` возвращает `skill_changes` с полями
`before`, `after`, `gain`, `max_level`, `applied_gain`, а также
`readiness_before`, `readiness_after`, `gaps_before`, `gaps_after` и
`recommendations_after`. Это предварительный расчёт через тот же доменный
механизм, что и реальное завершение: гипотетическая запись `completed` влияет
на рекомендации после активности. Запрос ничего не записывает в базу и не
отмечает активность выполненной. Для исходного E001 / EV002 готовность меняется
с ~81.73% на ~86.54%, System Design — с 2 на 3. Реальное начисление требует
отдельного `POST .../complete`.

`GET /employees/E001/comparison-options` возвращает все подходящие варианты в
том же формате, что `/recommendations`, но без ограничения первыми тремя.
`GET /employees/E001/compare?first_event_id=EV002&second_event_id=EV003`
сравнивает любые две активности, которые сейчас активны, доступны роли и
сокращают разрыв следующего грейда, в том числе вне топ-3. Поля `first` и
`second` содержат те же компоненты оценки, что рекомендации: `score`,
`grade_gap_benefit`, `skill_impact`, `participation`, `history_multiplier`,
`explanation`. Также возвращаются `readiness_after_first`,
`readiness_after_second`, `preferred_event_id`, `score_delta` и общее
`explanation`. Выбор определяется оценкой сокращения разрыва с учётом истории,
а не только изменением процента готовности; при равенстве решает `event_id`.
Одинаковые ID дают 422 `same_event`, активность без полезного воздействия —
422 `not_relevant`. Прогноз и сравнение требуют тех же прав на профиль, что и
обычные рекомендации.

## Необязательный GPT-выбор

`POST /employees/E001/ai/recommendations` берёт до 12 лучших допустимых
активностей из локального алгоритма и просит модель выбрать один `event_id`.
Модель не может добавлять активности, менять уровни навыков или писать в базу.
Выбранный вариант становится первым из максимум трёх; остальные берутся из
детерминированного ранжирования. Все числовые факторы и объяснение активности
рассчитаны backend, а не сочинены моделью. GPT может выбрать вариант ниже
первого по локальной оценке, поэтому `source=gpt` не означает, что его score
наибольший. `considered_count` — число допустимых вариантов, переданных модели
(не более 12).

Ключ задаётся только переменной окружения `OPENAI_API_KEY` процесса backend,
например в защищённых настройках запуска. Не добавляйте его в Git, JSON,
frontend или Swagger. В запрос к OpenAI передаются роль и грейды, ID вариантов,
числовые разрывы и приросты навыков, агрегированные счётчики истории и оценки.
Имя сотрудника, его ID, даты и отдельные записи истории не отправляются.
У запроса `store=false`; при использовании внешнего API всё равно учитывайте
политику обработки данных организации. Время ожидания — до 7 секунд; endpoint
может быть медленнее обычного локального ответа. Каждый вызов с ключом может
расходовать лимит API.

При отсутствии ключа, сбое провайдера или некорректном ID модельного ответа
возвращаются обычные первые три рекомендации: `source=rules` и
`fallback_reason=not_configured`, `provider_unavailable` или `invalid_response`.
При отсутствии подходящих активностей внешний запрос не делается.
`selected_event_id`, `selection_explanation`, `model` и `considered_count`
позволяют увидеть, какой путь сработал. Обычный `GET /recommendations` остаётся
полностью локальным и не расходует API-вызовы. Проверить GPT endpoint можно
через Swagger или HTTP-клиент. В контейнере его полный путь —
`POST /api/employees/{id}/ai/recommendations`.

В настоящем режиме frontend вызывает endpoint только после нажатия
**Подобрать с GPT** в профиле. Блок показывает источник и причину fallback,
выбранную активность и фактическое объяснение; из него доступны прогноз и
завершение. Открытие страницы само по себе не вызывает платный API.
## Выполнение активности

Обязателен заголовок `Idempotency-Key` со значением UUID, созданным клиентом для
одной попытки. При сетевом повторе используйте тот же ключ: повтор возвращает
исходный ответ (и тот же статус) с `Idempotency-Replayed: true`, без второго
прироста. Ключ хранится в базе и переживает перезапуск; для другого сотрудника или
события тот же ключ даёт 409. Область ключа — учётная запись.

**Режим `approval`** (продакшн по умолчанию). Запрос сотрудника не меняет навыки:
создаётся заявка и возвращается `202` `{"status":"pending_approval","request":{...}}`.
Необязательное тело `{"comment":"..."}` увидит HR. Повторная заявка на ту же
активность, пока первая не рассмотрена, даёт 409 `request_pending`. HR подтверждает
(`POST /completion-requests/{id}/approve`) — только тогда применяется прирост и
появляется запись истории; отклонение (`/reject`) ничего не меняет. Запрос HR к
`/complete` применяется сразу. Замена всего набора переводит открытые заявки в
`expired`.

**Режим `instant`** (разработка, демо): изменения применяются сразу, ответ 200.

Для каждого навыка активности:

```text
after = max(before, min(before + gain, max_level))
gain_applied = after - before
```

Уровень не понижается, если сотрудник уже выше max_level. Отсутствующий навык
имеет уровень 0. Архивные события и события для другой роли завершать нельзя.
Дата новой записи истории — текущая дата UTC на сервере.

Ответ 200 содержит `employee_id`, `event_id`, `record_id`, `skill_changes`,
`readiness_before`, `readiness_after`, `skill_gaps` и `recommendations`.
Изменение профиля, запись истории, ключ повтора и запись журнала сохраняются одной
транзакцией; запись одного сотрудника затрагивает только его строки. Ошибка
проверки не оставляет частичных изменений.

### Пропуск и отказ

`POST .../skip` и `.../decline` добавляют запись `skipped` или `declined`, навыки не
меняются. Ответ содержит `record_id` и пересчитанные `recommendations_after`:
история снижает множитель похожих активностей. `Idempotency-Key` необязателен,
но интерфейс его передаёт, чтобы двойной клик не создал две записи.

### Повышение грейда

`POST /employees/{id}/promote` (HR). Без тела переводит на следующий грейд трека,
только если `meets_mandatory=true`; иначе 422 `requirements_not_met`. Исключение —
`{"force": true, "reason": "Решение комиссии ..."}`: причина обязательна и
сохраняется в журнале. Для последнего грейда — 422 `top_grade`.

## Импорт

`POST /dataset/import` принимает multipart/form-data:

- `mode`: `append` (по умолчанию) или `replace`;
- `dry_run`: `true` — только проверить и показать изменения, ничего не записывая;
- `employees`: файл employees.json;
- `events`: файл events.json;
- `skills`: файл skills.json;
- `activity_history`: файл activity_history.csv.

Имена полей важны; исходные имена файлов не используются как пути. Каждый файл —
до 5 MiB, UTF-8, BOM допускается. Формат совпадает с документированным внутренним
контрактом. Неизвестная схема стартового кита автоматически не поддерживается.

В режиме `append` можно добавить новые профили, события и записи истории, включая
историю уже существующего сотрудника. Передавать `skills` нельзя. Существующие ID
не перезаписываются: коллизия отклоняется. Новые профили и история проверяются
вместе. Импортированные текущие навыки — снимок: история не начисляет gain повторно.

В режиме `replace` обязательны все четыре файла; они полностью заменяют набор.
Старый ключ завершения после замены даст 409 `dataset_replaced`. Учётные записи не
меняются: если привязанного профиля больше нет, запрос вернёт 404.

Перед каждым импортом и восстановлением текущее состояние сохраняется в снимок
(`GET /dataset/snapshots`, хранится `CAREER_QUEST_SNAPSHOT_KEEP` последних).
Весь предложенный набор проверяется до сохранения; при ошибке данные остаются
прежними. Стартовые файлы в `backend/data/` не изменяются.

## Журнал действий

`GET /audit` возвращает до 500 записей (`limit`), постранично через `before_id`.
Записываются: входы и неудачные попытки, смена и сброс пароля, согласие и отзыв,
создание и отключение учётных записей, просмотр профиля сотрудника HR, выполнение,
пропуск и отказ, заявки и решения, повышение грейда, импорт, снимки, восстановление,
выгрузка, вызовы GPT. Пароли и токены в журнал не попадают. Срок хранения задаёт
оператор: `python -m backend.manage purge-audit --days 365`.

## Проверочный сценарий

1. Войти сотрудником E001, сменить временный пароль, дать согласие.
2. Первым для исходного демо будет EV002 (Architecture Mentoring); посмотреть его
   прогноз и сравнить с EV003 (Public Speaking Meetup). До выполнения профиль и
   история не меняются.
3. Выполнить EV002. В `approval` — получить 202, войти HR и подтвердить заявку.
   System Design `2 → 3`, readiness `81.73% → 86.54%`.
4. Повторить запрос с тем же UUID: ответ тот же, второго прироста нет.
5. Перезапустить сервер и проверить, что навык и история сохранились.
6. Под HR открыть dashboard, импортировать новый профиль с проверкой без записи,
   затем по-настоящему; убедиться, что появился снимок.
7. Проверить, что сотрудник получает 403 на чужой профиль, HR-маршруты, импорт,
   журнал и управление учётными записями.

Тесты:

python -m pip install -r backend/requirements-dev.txt
python -m unittest discover -s backend/tests -v
