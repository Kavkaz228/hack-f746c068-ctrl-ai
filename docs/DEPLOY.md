# Развёртывание Career Quest

Три варианта:

| Вариант | Для чего | Данные |
| --- | --- | --- |
| [Сервер с HTTPS](#продакшн-на-своём-сервере) — `deploy/compose.prod.yaml` | Коммерческая эксплуатация | Реальные сотрудники; сервер в РК |
| [Docker Compose локально](#docker-compose-локально) — `compose.yaml` | Проверка, пилот внутри сети | Любые, если машина в РК |
| [Render](#демо-на-render) — `render.yaml` | Показ жюри по ссылке | **Только синтетические** |

Закон РК «О персональных данных и их защите» (ст. 12) требует хранить базы
с персональными данными граждан РК на территории РК. Для реальных сотрудников
выбирайте VPS или собственный сервер в казахстанском дата-центре. Юридические
вопросы — в [docs/legal](legal/README.md).

## Продакшн на своём сервере

Требования: Linux-сервер (2 vCPU, 2–4 ГБ RAM, 20 ГБ диска хватает на десятки
тысяч сотрудников), Docker Engine с Compose v2, домен с A-записью на сервер,
открытые порты 80 и 443.

1. Клонируйте репозиторий на сервер и создайте `.env` в корне:

   ```sh
   cp .env.example .env
   ```

   Заполните: `POSTGRES_PASSWORD` (длинная случайная строка из букв и цифр,
   например `openssl rand -hex 24`), `CAREER_QUEST_DOMAIN`, `ACME_EMAIL`,
   `CAREER_QUEST_BOOTSTRAP_HR_EMAIL` и временный `CAREER_QUEST_BOOTSTRAP_HR_PASSWORD`
   (не короче 10 символов, буквы и цифры). При желании — `CAREER_QUEST_METRICS_TOKEN`
   и `OPENAI_API_KEY`. Права на файл: `chmod 600 .env`.

2. Запустите:

   ```sh
   docker compose -f deploy/compose.prod.yaml --env-file .env up --build -d
   ```

   Caddy получит сертификат Let's Encrypt и начнёт отдавать сайт по
   `https://<CAREER_QUEST_DOMAIN>`. База находится во внутренней сети без выхода
   наружу; порт приложения не публикуется.

3. Войдите первым HR, задайте постоянный пароль, дайте согласие. После этого
   удалите `CAREER_QUEST_BOOTSTRAP_HR_PASSWORD` из `.env` (повторно учётная запись
   не создаётся, но пароль не должен лежать на диске).

4. Загрузите реальные данные: «Управление» → «Данные» → «Заменить всё» (все четыре
   файла) — сначала «Проверить без записи». Демо-набор при этом сохранится в снимок.
   Альтернатива: `docker compose -f deploy/compose.prod.yaml exec web python -m backend.manage import-dir /path`
   (каталог нужно смонтировать в контейнер).

5. Выдайте доступ сотрудникам: «Управление» → «Учётные записи». Временный пароль
   показывается один раз — передайте его лично или по защищённому каналу.

6. Настройте мониторинг и резервное копирование вне сервера —
   [OPERATIONS.md](OPERATIONS.md).

Обновление версии:

```sh
git pull
docker compose -f deploy/compose.prod.yaml --env-file .env up --build -d
```

Миграции схемы применяются автоматически при старте (с блокировкой, безопасно
для нескольких процессов). Перед обновлением сделайте снимок («Данные» → «Создать
снимок») или дождитесь ночной копии.

### Что настроено в compose.prod.yaml

| Компонент | Настройка |
| --- | --- |
| `caddy` | HTTPS, HTTP/3, сжатие, лимит тела 25 МБ, JSON-логи |
| `web` | `CAREER_QUEST_ENV=production`: подтверждение HR, скрытый Swagger, без демо-аккаунтов; 2 процесса; read-only файловая система; доверие `X-Forwarded-*` только от Caddy |
| `db` | PostgreSQL 16, сеть `internal` без выхода наружу |
| `backup` | `pg_dump` сразу и затем раз в сутки в `BACKUP_DIR` (абсолютный путь на сервере), хранение `BACKUP_KEEP_DAYS` дней |

## Docker Compose локально

```sh
cp .env.example .env    # POSTGRES_PASSWORD и первый HR обязательны
docker compose up --build -d
```

Сайт: `http://localhost:8000` (порт меняется `CAREER_QUEST_PORT`). Сервисы те же,
что в продакшне, но без Caddy и HTTPS: используйте внутри доверенной сети или
только локально. Логи: `docker compose logs --tail=100 web`.

## Демо на Render

`render.yaml` создаёт Web Service с диском для SQLite. Регион Render — Франкфурт,
поэтому загружайте только синтетические данные. Демо-режим:
`CAREER_QUEST_COMPLETION_MODE=instant` (выполнение засчитывается сразу).

1. Откройте [Blueprint](https://render.com/deploy?repo=https://github.com/BAITC-Hacks/hack-f746c068-ctrl-ai).
   Если Render пишет `cannot access the following repo`, установите GitHub App
   Render в организацию-владельца репозитория (может потребоваться одобрение владельца).
2. Задайте `CAREER_QUEST_BOOTSTRAP_HR_EMAIL` и `CAREER_QUEST_BOOTSTRAP_HR_PASSWORD`
   в панели (значения не хранятся в репозитории). При желании — `OPENAI_API_KEY`
   как секрет.
3. Дождитесь статуса **Live**, войдите HR, смените пароль, создайте учётную запись
   сотрудника для жюри и передайте её по закрытому каналу.

Платный план не засыпает и сохраняет диск между перезапусками; бесплатный
засыпает через 15 минут и теряет данные SQLite.
[Постоянные диски](https://render.com/docs/disks), [ограничения бесплатного плана](https://render.com/docs/free).

## Необязательный GPT

Задайте `OPENAI_API_KEY` в `.env` (или как секрет в панели хостинга) и перезапустите
`web`. Ключ не попадает в браузер, репозиторий и логи. В модель уходят только
обезличенные числовые признаки (уровни навыков, параметры активностей) — без имени,
почты, ID и дат. Лимит — `CAREER_QUEST_AI_DAILY_LIMIT` вызовов в сутки на
пользователя; без ключа работает локальный алгоритм.

## Автоматическая проверка

Workflow [.github/workflows/container.yml](../.github/workflows/container.yml)
при push в `main`, в pull request и вручную: тесты на SQLite и PostgreSQL, сборка
frontend, сборка образов, запуск `compose.yaml`, сквозная проверка
`backend.scripts.smoke_container` (вход паролем, роли, заявка и её подтверждение,
повтор запроса), перезапуск с проверкой сохранности и наличие резервной копии.

`smoke_container` создаёт две служебные учётные записи `smoke-*@smoke.invalid` и
выполняет одну активность — не запускайте его на базе с реальными данными.
