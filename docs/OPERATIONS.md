# Эксплуатация Career Quest

Команды ниже — для `deploy/compose.prod.yaml`; для локального `compose.yaml` уберите
`-f deploy/compose.prod.yaml`. Для краткости:

```sh
alias cq='docker compose -f deploy/compose.prod.yaml --env-file .env'
```

## Резервные копии

Сервис `backup` делает `pg_dump -Fc` при старте и раз в сутки, файлы
`career_quest-<UTC-время>.dump` лежат в `BACKUP_DIR` (в `.env.example` —
`/var/backups/career-quest`; если не задан — каталог `backups/` в корне репозитория),
старше `BACKUP_KEEP_DAYS` (14) удаляются. Проверка: `cq logs --tail=20 backup`.

Обязательно копируйте каталог копий **за пределы сервера** (другой сервер или
объектное хранилище в РК) и шифруйте при передаче и хранении, например:

```sh
gpg --encrypt --recipient ops@company.kz /var/backups/career-quest/career_quest-*.dump
```

Внеплановая копия:

```sh
cq exec backup sh -c 'pg_dump -Fc -f /backups/manual-$(date -u +%Y%m%dT%H%M%SZ).dump'
```

Кроме копий базы, приложение хранит **снимки набора данных** (сотрудники,
активности, навыки, история) перед каждым импортом и восстановлением —
«Управление» → «Данные». Это быстрый откат ошибочного импорта; учётные записи,
журнал и заявки снимки не затрагивают.

### Восстановление из копии

```sh
cq stop web
cq exec -T db pg_restore -U career_quest -d career_quest --clean --if-exists < /var/backups/career-quest/career_quest-20261005T000000Z.dump
cq start web
```

Проверяйте восстановление раз в квартал на отдельной машине: поднимите
`compose.yaml`, восстановите копию, войдите и откройте профиль.

### SQLite (разработка, Render)

```sh
python -m backend.manage backup-sqlite --output backup.sqlite3
```

Команда делает согласованную копию работающей базы.

## Мониторинг

| Проверка | Что означает |
| --- | --- |
| `GET /api/health` → 200 | Процесс отвечает (liveness) |
| `GET /api/ready` → 200 | База доступна, схема применена (readiness; использует healthcheck контейнера) |
| `GET /api/metrics` с `Authorization: Bearer <CAREER_QUEST_METRICS_TOKEN>` | Prometheus: запросы по статусам, суммарное время, uptime, версия данных |

Логи приложения — JSON в stdout, по одной строке на запрос: `request_id`,
метод, путь, статус, `duration_ms`. Тела запросов, пароли и cookie не логируются.
Сообщение пользователю об ошибке можно сопоставить с логом по заголовку
`X-Request-ID`. Пример: `cq logs web | grep '"status": 5'`.

Рекомендуемые оповещения: `ready` не 200 дольше минуты; доля 5xx > 1% за 5 минут;
нет нового файла копии за 26 часов; заканчивается место на диске; всплеск
`login_failed` в журнале.

## Учётные записи и инциденты

| Ситуация | Действие |
| --- | --- |
| Сотрудник забыл пароль | HR: «Учётные записи» → «Сбросить пароль» (или `cq exec web python -m backend.manage reset-password --email ...`) |
| Увольнение | «Отключить» — сессии завершаются сразу; профиль и история остаются для HR |
| Подозрение на компрометацию | Сбросить пароль, проверить «Журнал» (входы, IP, просмотры), при необходимости отключить |
| Ошибочный импорт | «Данные» → снимок «перед дозагрузкой/заменой» → «Восстановить» |
| Заблокирован после попыток входа | Блокировка снимается через 15 минут или сбросом пароля |
| Последний HR потерял доступ | `cq exec web python -m backend.manage create-user --email ... --role hr` |

Смена секретов: `POSTGRES_PASSWORD` — смените пароль роли в PostgreSQL
(`ALTER ROLE career_quest PASSWORD '...'`), затем `.env` и `cq up -d`.
`CAREER_QUEST_METRICS_TOKEN`, `OPENAI_API_KEY` — `.env` и `cq up -d web`.

## Хранение данных

- Журнал действий: `cq exec web python -m backend.manage purge-audit --days 365`
  (минимум 30 дней; удаляет и истёкшие сессии). Срок определяет политика оператора.
- Снимки данных: хранится `CAREER_QUEST_SNAPSHOT_KEEP` последних (20).
- Отзыв согласия закрывает доступ сотрудника; удаление его профиля выполняется
  импортом без него (`replace`) и подтверждается юристом.

## Производительность и масштабирование

Замер на 5000 сотрудниках, 24 тыс. записей истории, PostgreSQL 16, 2 процесса:

| Операция | Время |
| --- | --- |
| Список HR со всеми показателями (`/hr/employees`) | ~0,1 с |
| HR-аналитика (`/hr/dashboard`) | ~0,09 с; после изменений ~0,12 с |
| Профиль сотрудника | ~50 мс |
| 40 одновременных выполнений | без ошибок, медиана ~45 мс |
| Импорт 5000 сотрудников (`replace`) | ~1,2 с |

Показатели HR кэшируются в каждом процессе по версии данных; после изменения
пересчитываются только затронутые сотрудники. Масштабирование: увеличьте
`WEB_CONCURRENCY` (процессы) и `CAREER_QUEST_DB_POOL`; все записи сериализуются
в базе, поэтому несколько процессов и серверов безопасны. Ограничение частоты
входа считается в каждом процессе отдельно.
